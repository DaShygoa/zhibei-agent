# Prompt 设计文档

源码：`zhibei/prompts.py`

## 1. 结构

| 段落 | 作用 | 设计理由 |
|---|---|---|
| 角色 | 定位为"备考教练"，目标是诊断→抽题→判分→讲解→再推荐 | 明确任务闭环，防止退化为闲聊机器人 |
| 工具清单 | 一句话说明每个工具 | 工具 docstring 已经很详细，这里只给全局地图 |
| 决策规则 | 6 条"用户意图 → 调用哪个工具、参数怎么填" | Function Calling 模型在意图模糊时容易不调工具或调错，显式规则可以提高稳定性 |
| 输出格式 | 题目展示格式、判分结果格式、字数限制 | 保证 UI 展示统一，便于用户按格式作答 |
| 禁止事项 | 判分前不透露答案、不编题、不凭记忆判分、无依据要标注 | 对应本项目最大的风险：幻觉与作弊 |
| 长期记忆注入 | `{profile_brief}` 每轮由数据库生成 | 让模型"记得"用户的薄弱点，即使对话是新开的 |
| Few-shot | 3 个"用户输入 → 思考 → 工具调用"示例 | 只示范决策，不示范长回复，节省 token |

## 2. 关键 Prompt 原文

见 `SYSTEM_PROMPT`、`FEW_SHOT`、`FORCE_FINISH` 三个常量。

`FORCE_FINISH`（超过步数上限时追加）：
> 你已经连续调用了很多次工具。请不要再调用任何工具，直接根据已有的工具结果给用户一个完整、简洁的回答。

## 3. 迭代记录

| 版本 | 改动 | 原因 |
|---|---|---|
| V0（Dify 原版） | 3 段独立 Prompt：关键词抽取 / 出 7 道题 / 讲解 | 见 dify_vs_langgraph.md，存在要求矛盾、LLM 编题等问题 |
| V1 | 合并为单一 Agent System Prompt；出题改为调用 `draw_quiz` 抽真题 | 从"生成"改为"检索+工具"，消除编题幻觉 |
| V2 | 增加"判分只能来自 grade_answers""判分前不透露答案"禁止项；增加 Few-shot 决策示例 | 工具描述里已写，但放在 System Prompt 中约束力更强 |
| V3（LangGraph） | 评测 12/13：C11"错题本为空"Agent 先调用 get_mistakes 确认为空再引导用户，行为正确但用例要求必须调用 draw_quiz。**改评测用例**（must_call_any），不改 Prompt | 区分"Agent 错"与"用例写死"，避免为迎合用例把正确行为改坏 → 13/13 |
| D1（Dify） | 迁移到 Dify Agent：抽题/判分改为工作流工具，新增"测验码"规则（原样展示、原样回传） | Dify Agent 记忆只有 2000 tokens，靠测验码让判分不依赖记忆 |
| D2（Dify） | 冒烟测试发现作答示例写成"4BCD 5对"，像答案提示 → 固定示例「1A 2BC 3对」 | 防止误导用户 |
| D3（Dify） | 评测 D09 发现**真实缺陷**：未抽题时用户报答案，Agent 竟自行抽题再拿这串答案判分（0/3）。增加前置条件：本次对话未展示过测验码时不得判分 | 防止"自作主张的规划"产生无意义结果；修复后 D09 通过 |

## 4. 工具描述（docstring）也是 Prompt

LLM 选择工具时主要看工具的 description 和参数说明，因此每个工具的 docstring 都写清楚了：
- **何时调用**（如 search_knowledge："讲解概念、分析错因……时先调用它，避免凭空编造"）
- **参数取值范围与示例**（如 answers 的 `answer` 字段："'B'、'ACD'、'对'、'PEFT'"）
- **调用后应该做什么**（如 draw_quiz："抽题后，必须把题目原样展示给用户，并等待用户作答"）
